# Техническое задание: Spoti-Chan

**Дата:** 29.10.2026  
**Тип проекта:** учебное веб-приложение для поиска и открытия музыки  
**Текущая версия:** v0.2 — frontend и демонстрационный backend

## 1. Назначение и границы проекта

Spoti-Chan — музыкальный сервис с каталогом треков, избранным и Music Finder: поиском по текстовому описанию. Целевой сценарий: пользователь не помнит название композиции либо хочет найти похожее звучание и вводит, например, «Что-то похожее на Linkin Park, но с женским вокалом».

Разработка ведётся небольшими законченными этапами. Этот документ фиксирует поведение реализованной v0.2 и отдельно определяет последующие этапы полного MVP. Указание будущей функции не означает, что она уже доступна.

| Область | Реализовано в v0.2 | Запланировано для полного MVP |
| --- | --- | --- |
| Интерфейс | Обзор, каталог, Music Finder, избранное, сведения о треке | Работа с музыкальным каталогом внешнего сервиса и плеером |
| Каталог | Четыре записи в файле backend, только метаданные | Получение доступных треков из Jamendo и хранение данных в Firestore |
| Поиск по описанию | Правила, жанры, известные исполнители, тип вокала | Извлечение параметров свободного описания через Gemini |
| Избранное | Список идентификаторов в localStorage | Хранение предпочтений после проектирования модели данных |
| Воспроизведение | Отсутствует | Плеер для доступных по условиям музыкального API треков |
| Размещение | Локальный запуск, раздача сборки через Express | Firebase Hosting для frontend, Cloud Run для backend |

Персональные ИИ-рекомендации, полноценное распознавание естественного языка, учётные записи и управление музыкальным каталогом через административную панель в текущую версию не входят. Сроки, стоимость облачных сервисов и количественные показатели нагрузки этим ТЗ не устанавливаются.

## 2. Пользователи и архитектура

### 2.1. Роль пользователя

Единственная роль v0.2 — **гость**. Вход и регистрация отсутствуют. Гость просматривает каталог, применяет фильтры, отправляет описание в Music Finder, открывает сведения о треке и меняет избранное в своём браузере. Сервер не создаёт профиль и не синхронизирует избранное между устройствами.

### 2.2. Технологии

| Компонент | Назначение | Статус |
| --- | --- | --- |
| React | Компоненты, состояние экранов и взаимодействия | Реализовано |
| Tailwind CSS и CSS | Оформление, адаптивные состояния | Реализовано |
| Vite | Сервер разработки и сборка frontend | Реализовано |
| Node.js + Express | HTTP API и раздача готового frontend | Реализовано |
| Firestore | База треков и предпочтений | Запланировано |
| Gemini API | Извлечение музыкальных признаков из описания | Запланировано |
| Jamendo API | Источник музыкальных метаданных и аудио | Запланировано |

В текущей архитектуре браузер отправляет HTTP-запросы в Express. В разработке Vite проксирует `/api` на `http://127.0.0.1:3001`. После сборки Express раздаёт каталог `dist`, поэтому frontend и API работают с одного origin. Навигация реализована через hash: `#/`, `#/finder`, `#/favorites`; для переходов между экранами не требуется отдельный серверный маршрут.

## 3. Функциональные требования v0.2

### 3.1. Общий интерфейс и навигация

Интерфейс русскоязычный, с тёмной темой и зелёным акцентом. Основная навигация содержит «Обзор», «Music Finder», «Избранное» и обозначает выбранный экран. На узких экранах навигация перемещается в нижнюю область. Заголовок вкладки соответствует открытому разделу.

Обозначение деморежима должно оставаться видимым. Графика на карточках создаётся средствами интерфейса и является декоративной, а не настоящими обложками альбомов. Интерфейс не должен выдавать отсутствие аудио за работающее воспроизведение.

### 3.2. Обзор и каталог

Экран обзора содержит вводный блок с переходом в Music Finder и каталог, полученный через `GET /api/tracks`.

Карточка трека показывает декоративную графику, название, исполнителя, основной жанр, тип вокала и кнопку избранного. Нажатие на графику или название открывает диалог со сведениями о треке.

Пользователь может:

- Искать подстроку в названии или имени исполнителя без учёта регистра. Пробелы по краям запроса удаляются.
- Выбирать один фильтр: «Все треки», «Рок», «Метал», «Поп», «Танцевальная». Фильтр проверяет наличие соответствующего тега.
- Совмещать строковый поиск и выбранный жанр; отображаются только записи, удовлетворяющие обоим условиям.
- Видеть количество отображаемых записей.

Во время загрузки выводится индикатор. При ошибке запроса отображаются сообщение и кнопка повтора. При отсутствии подходящих записей показывается отдельное пустое состояние с предложением изменить поиск или фильтр.

### 3.3. Music Finder

Экран содержит поле описания, счётчик символов, кнопку «Найти музыку», примеры запросов, пояснение деморежима и область результатов.

Порядок работы:

1. Пользователь вводит от 1 до 500 символов либо выбирает пример. Пример только заполняет поле; запрос отправляется кнопкой формы.
2. Пустой ввод или одни пробелы не отправляются. Пробелы по краям удаляются перед отправкой.
3. Frontend передаёт JSON с `description` в `POST /api/finder`.
4. На время запроса поле, примеры и кнопка отправки блокируются. Предыдущие результаты очищаются, выводится индикатор поиска.
5. Ответ отображается в порядке, полученном от API. Строка результата содержит название, исполнителя, совпавшие теги, вокал и кнопку избранного. Можно открыть сведения о треке.

Начальное состояние приглашает описать музыку. Пустой ответ отображается как отсутствие совпадений с подсказками. При сетевой или серверной ошибке введённый текст сохраняется для повторной отправки. Кнопка «Сбросить» отменяет незавершённый запрос, очищает поле, результаты и ошибку, возвращает фокус в поле. Уход с экрана отменяет выполняющийся запрос; состояние формы не сохраняется между посещениями раздела.

### 3.4. Правила демонстрационного подбора

Backend использует словарь правил, а не генеративную модель. Распознаются исполнители Linkin Park, Evanescence, Within Temptation, Daft Punk; теги `rock`, `metal`, `alternative`, `symphonic`, `pop`, `funk`, `dance`, `energetic` и предусмотренные русские формы этих слов. Тип вокала определяется по женскому/female или мужскому/male.

Известный исполнитель преобразуется в набор жанровых тегов. После этого:

- Явно указанный тип вокала применяется как фильтр.
- При наличии распознанных тегов выбираются треки с хотя бы одним совпавшим тегом.
- При запросе только о типе вокала возвращаются все соответствующие ему записи, даже без совпавших тегов.
- Результаты упорядочиваются по убыванию количества совпавших тегов; равные результаты сохраняют порядок каталога.
- Если не распознаны ни теги, ни вокал, результат пустой. Если одновременно указаны мужской и женский вокал, результат также пустой.

Пример с Linkin Park и женским вокалом должен вернуть **Going Under — Evanescence**, затем **Ice Queen — Within Temptation**. Сложные отрицания, настроение вне словаря, поиск по напетой мелодии и смешанный вокал не поддерживаются. Совпадения не являются гарантией акустического сходства или нахождения конкретной забытой песни.

### 3.5. Избранное и сведения о треке

Кнопка сердечка добавляет идентификатор трека в избранное либо удаляет его. Состояние должно согласованно отражаться в каталоге, Finder и диалоге. Экран избранного показывает сохранённые записи текущего каталога и поддерживает те же поиск и жанровый фильтр. Если ничего не сохранено, выводится приглашение добавить треки.

Список хранится под ключом `spoti-chan:favorites:v1` в localStorage как массив строковых идентификаторов. Он сохраняется только в данном браузере и origin: смена протокола, домена или порта создаёт отдельное хранилище. Очистка данных браузера удаляет избранное. При невозможности чтения или записи выводится предупреждение; если запись запрещена, изменения доступны в памяти текущей сессии.

Диалог трека содержит название, исполнителя, все теги, тип вокала, кнопку избранного и пояснение об отсутствии воспроизведения. Закрытие доступно отдельной кнопкой, клавишей Escape и нажатием на фон за пределами диалога.

## 4. Данные и текущий HTTP API

### 4.1. Модель трека

| Поле | Тип | Значение |
| --- | --- | --- |
| `id` | string | Уникальный идентификатор записи |
| `title` | string | Название композиции |
| `artist` | string | Исполнитель |
| `vocals` | `female` или `male` | Тип вокала для демонстрационного фильтра |
| `tags` | string[] | Жанровые и музыкальные теги |
| `matchedTags` | string[] | Только в результатах Finder: совпавшие теги |

Исходный каталог: `1` — Going Under / Evanescence, `2` — Ice Queen / Within Temptation, `3` — Numb / Linkin Park, `4` — Get Lucky / Daft Punk. Записи не содержат аудиофайлов, URL для воспроизведения, длительностей и настоящих обложек. Каталог хранится в `server/catalog.js`; операции добавления, изменения и удаления через API отсутствуют.

### 4.2. Методы

| Метод и путь | Вход | Успешный ответ |
| --- | --- | --- |
| `GET /api/health` | Нет | `200`, `{ "status": "ok" }` |
| `GET /api/tracks` | Нет | `200`, `{ "tracks": [...] }` |
| `POST /api/finder` | `Content-Type: application/json`, объект с `description` | `200`, `{ "mode": "demo-tags", "tracks": [...] }` |

Пример запроса Finder:

```json
{ "description": "Что-то похожее на Linkin Park, но с женским вокалом" }
```

Сервер требует строку `description`, непустую после удаления краевых пробелов, длиной не более 500 символов в исходном поле. Ограничение длины соответствует JavaScript `String.length`. JSON-тело ограничено 8 КБ. Пустая выдача — успешный ответ с `tracks: []`, а не ошибка.

Ошибки существующих обработчиков возвращаются в JSON с полем `error`:

- `400`: отсутствующее, пустое, неверного типа или слишком длинное описание — «Описание должно содержать от 1 до 500 символов.»; некорректный JSON — «Некорректное тело запроса.».
- `413`: превышен лимит тела запроса — «Некорректное тело запроса.».
- `500`: внутренняя ошибка — «Ошибка сервера.».

Неизвестные маршруты используют стандартный ответ Express `404`; единый JSON-формат для них пока не предусмотрен. Пагинации, параметров серверного фильтра каталога и API избранного нет. Frontend проверяет структуру ответов каталога и Finder; неверный JSON или неизвестная структура должны приводить к понятному сообщению, а не падению интерфейса.

## 5. Нефункциональные требования и запуск

- Адаптивность: основные экраны и диалог пригодны для узкого мобильного экрана и настольного окна; элементы не перекрывают основные действия.
- Доступность: семантические кнопки и ссылки, подписи полей, заметный фокус, управление клавиатурой, сообщения о загрузке/результате/ошибке для вспомогательных технологий. Ссылка «К содержимому» переводит фокус, не меняя раздел.
- Устойчивость: недоступность API, пустая выдача и заблокированный localStorage имеют отдельные состояния; повтор не требует перезагрузки страницы.
- Безопасность: описание передаётся как текст, не вставляется как HTML. Будущие ключи Gemini и Jamendo должны находиться на backend, вне репозитория и клиентской сборки.
- Воспроизводимость: зависимости фиксируются lock-файлом; сборка и автоматические проверки должны завершаться без ошибок. Версии зависимостей определяются `package.json` и `package-lock.json`.

Для локальной работы нужны Node.js 22.12+ и npm. Установка и запуск готовой сборки:

```sh
npm ci
npm run build
npm start
```

Приложение открывается на `http://localhost:3001`. Переменная `PORT` меняет порт Express. В разработке `npm run dev` запускает API и Vite одновременно; frontend доступен на адресе, который выводит Vite, по умолчанию `http://127.0.0.1:5173`. Для раздельного запуска используются `npm run dev:server` и `npm run dev:client` в разных терминалах. Proxy frontend настроен на порт API `3001`; при его изменении настройку proxy необходимо согласовать. `npm run preview` показывает сборку Vite и также требует отдельно работающий API. Автоматические проверки запускаются командой `npm test`.

## 7. Последующие этапы полного MVP

1. **Музыкальный API и плеер.** Подключить Jamendo через backend, нормализовать метаданные, использовать доступные аудиоисточники. Добавить выбор трека, воспроизведение/паузу, прогресс и громкость; обработать недоступность аудио. Проверить условия использования и атрибуции каталога перед распространением. Демонстрационные названия текущего каталога не гарантируются в Jamendo.
2. **Реальный Music Finder.** Подключить Gemini на сервере для преобразования описания в проверяемые жанры, исполнителей и теги. Искать по доступному каталогу, показывать причины подбора. Различать ошибку модели, отсутствие совпадений и ошибку музыкального API; не подменять найденный трек выдуманным результатом.
3. **Firestore и рекомендации.** Спроектировать коллекции треков и предпочтений, правила доступа и способ идентификации пользователя до включения облачного сохранения. Добавить рекомендации по подтверждённым предпочтениям и понятный сценарий пустого профиля. Требования к регистрации и синхронизации при необходимости оформить отдельно.
4. **Облачное размещение.** Разместить frontend на Firebase Hosting, backend на Cloud Run. Настроить адрес API, разрешённые origin, переменные окружения и доступ к внешним сервисам. Приёмка этапа: опубликованный frontend выполняет реальные запросы к backend, секреты отсутствуют в сборке, ошибки интеграций отображаются пользователю.

Каждый этап оформляется самостоятельным изменением с проверками и обновлением документации. Окончательный объём полного MVP уточняется по доступности внешних API и результатам предыдущего этапа.
